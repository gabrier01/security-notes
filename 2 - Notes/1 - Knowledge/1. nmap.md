O `nmap` é uma ferramenta de código aberto usada para descoberta de hosts e varredura de portas em redes. Ele permite identificar quais [[5. Host]]s estão ativos, quais portas estão abertas, quais serviços estão rodando e até o sistema operacional dos alvos.

# Host Discovery

Após identificar todos os [[5. IP (Address)|IPs]] e [[5. Net Blocks|blocos de rede]] pertencentes ao alvo (ver [[6. Enumerar IPs do Alvo]]), uma das etapas mais importantes é descobrir quais [[5. Host|hosts]] estão ativos, ou seja, quais respondem a pacotes enviados. Esse tipo de processo se chama **Host Discovery** ou **Ping Scanning**

Essa identificação é essencial para filtrar os alvos reais dentro de uma lista ampla de endereços, otimizando tempo e recursos nas etapas seguintes, como [[#Port Scanning]], enumeração de serviços e exploração.

Para realizar um **Host Discovery** básico, basta executar o `nmap` com a opção `-sn`, desabilitando qualquer tipo de port scanning a não ser o mínimo necessário para verificar se o host está ativo:

```shell
$ nmap -sn example.com
```

Ao final, será apresentado [[#Dicas para **Host Discovery**|Dicas para Host Discovery]]
## Técnicas de Host Discovery

Técnicas de **Host Discovery** são chamadas de **ping types**. Por padrão, o `nmap` realiza quatro **ping types** distintos, sendo eles:

- `-PE`: [[#ICMP Echo Request]]; envia um pacote `icmp echo request (type 8)`.
- `-PP`: [[#ICMP Timestamp Request]]; envia um pacote `icmp timestamp request (type 13)`
- `-PS443`: [[#TCP Syn Scan]]; envia um **raw packet** [[5. TCP|TCP]] com a flag `SYN` para a porta `443`.
- `-PA80`: [[#ACK Scan]]; envia um **raw packet** TCP com a flag `ACK` para a porta `80`.

```shell
# ou seja
$ nmap -sn example.com
# é equivalente à
$ nmap -sn -PE -PP -PS443 -PA80 example.com
```

> [!info] ARP Scanning
> O `nmap` também é capaz de enviar um pacote [[5. ARP (Protocol)|ARP]] se, e somente se, o host alvo estiver na mesma rede.

> [!info] Pacotes de Retorno
> As técnicas de **Host Discovery** não se importam com o tipo de pacote obtido como resposta, apenas se houve alguma resposta; se algum pacote é recebido do host, portanto está ativo.

Algumas técnicas utilizadas para **Host Discovery** também são técnicas de **Port Scanning**. Se for o caso, cada seção explicativa de um **ping type** irá redirecionar para a seção de **Port Scanning** respectiva.

### TCP SYN Ping
[source](https://nmap.org/book/host-discovery-techniques.html#host-discovery-PS)

```shell
$ nmap -sn -PS[ports] example.com
```

A opção `-PS` faz com que o `nmap` envie um pacote TCP contendo apenas a flag `SYN` para as portas especificadas em `[ports]`; se nenhuma porta for informada, a `80` é usada como padrão. 

Por se tratar também de uma técnica de **Port Scanning**, mais detalhes podem ser encontrados em [[#TCP Syn Scan]].

### TCP ACK Ping
[source](https://nmap.org/book/host-discovery-techniques.html#host-discovery-PA)

```shell
$ nmap -sn -PA[ports] example.com
```

A opção `-PA` faz com que o `nmap` envie um pacote TCP contendo apenas a flag `ACK` para as portas especificadas em `[ports]`; se nenhuma porta for informada, a `80` é usada como padrão. 

Por se tratar também de uma técnica de **Port Scanning**, mais detalhes podem ser encontrados em [[#ACK Scan]].

> [!redteam] ACK Ping vs Firewall
> Dificilmente pacotes TCP que possuem apenas a flag `ACK` são rejeitados por regras de Firewall. Isso acontece, pois esses pacotes facilmente se passam por pacotes legítimos. Para que o Firewall possa identificar `ACK` ilegítimos, ou seja, que não fazem parte de uma conexão real, ele teria que manter [[5. Firewall#Stateful Firewall|estado]] das conexões abertas, consumindo mais recursos do host.

### UDP Ping
[source](https://nmap.org/book/host-discovery-techniques.html#host-discovery-PU)

```shell
$ nmap -sn -PU[ports] example.com
```

A opção `-PU` faz com que o `nmap` envie um pacote [[5. UDP|UDP]] para as portas especificadas em `[ports]`; se nenhuma porta for informada, a `40125` é usada como padrão.

A intenção desse **ping type** é de atingir alguma porta que **não** esteja aberta (por isso o padrão é `40125`), esperando algum pacote como retorno, geralmente `icmp port unreachable`. A intenção pode parecer contraintuitiva, mas como UDP não é orientado a conexão, serviços executando em portas abertas não são obrigados a responder.

### ICMP Ping (`-PE, -PP e -PM`)
[source](https://nmap.org/book/host-discovery-techniques.html#host-discovery-icmpping)

```shell
$ nmap -sn -PE example.com
$ nmap -sn -PP example.com
$ nmap -sn -PM example.com
```

As opções `-PE`, `-PP` e `-PM` enviam pacotes [[5. ICMP|ICMP]] `echo  request (type 8)`, `timestamp request (type 13)` e `mask request (type 17)`, respectivamente.

Como ICMP não é um protocolo da camada de transporte, não há porta para ser especificada.

> [!info] Bloqueios ICMP
> Geralmente pacotes ICMP do tipo `echo request` são bloqueados e hoje em dia `timestamp request` e `mask request` são raramente suportados.

### IP Protocol Ping
[source](https://nmap.org/book/host-discovery-techniques.html#host-discovery-PO)

```shell
$ nmap -sn -PO[protocol list] example.com
```

A opção `-PO` envia pacotes [[5. IP (Address)|IP]] com os números de protocolo especificados no parâmetro `[protocol list]`; se nenhum valor for informado, por padrão o `nmap` envia `ICMP (1)`, `IGMP (2)` e `IP-in-IP (4)`. 

> [!info] Abranger diferentes métodos de ping
> Em ambientes restritivos, testar diferentes tipos de protocolos suportados pela pilha IP pode ser útil para tentar adquirir alguma resposta do host.

## Dicas para **Host Discovery**
[source](https://nmap.org/book/host-discovery-strategies.html#host-discovery-ideal-probes)

### Parâmetros interessantes
- `-n`: desativa [[6. Resolução Reversa de DNS]]; pode melhorar significativamente a velocidade de execução para muitos endereços IP.
- `-g[port]` ou `--source-port [port]`: permite especificar a porta de origem dos pacotes criados; pode melhorar significativamente a taxa de resposta se usado com a porta `53` (ver [Source Port Manipulation](https://nmap.org/book/firewall-subversion.html#defeating-firewalls-source-port) para mais detalhes do porquê).
- `--reason`: especifica a técnica utilizada que revelou a disponibilidade do host.
- `--data-length [length]`: adiciona um payload aleatório de `length` bytes ao pacote; útil para fazer bypass em [[5. IDS]] que possui alertas para pacotes sem payload. Exemplos: `32` pode simular um `icmp echo request` originado de um **Windows**, enquanto `54` de um **Linux**. É comum também informar `24`, valor adquirido através de heurística.

### Combinação de técnicas

A documentação oficial do `nmap` lista uma série de combinações de técnicas de **Host Discovery** que possuem alta probabilidade de descoberta. Isso pode ser visto com mais detalhes [aqui](https://nmap.org/book/host-discovery-strategies.html#host-discovery-tbl-best-combinations):

| Qnt Pacotes | % de Hosts Descobertos | Combinação                                                   |
| ----------- | ---------------------- | ------------------------------------------------------------ |
| 1 probe     | 62.47%                 | `-PE`                                                        |
| 2 probes    | 77.61%                 | `-PE -PA80`                                                  |
| 3 probes    | 83.83%                 | `-PE -PA80 -PS443`                                           |
| 4 probes    | 88.64%                 | `-PE -PP -PA80 -PS443`                                       |
| 5 probes    | 91.12%                 | `-PE -PP -PA80 -PS443 -PU40125 --source-port 53`             |
| 6 probes    | 92.42%                 | `-PE -PP -PS80,443 -PU40125 -PA3389 --source-port 53`        |
| 7 probes    | 93.10%                 | `-PE -PP -PS80,443,3389 -PU40125 -PA21 --source-port 53`     |
| 8 probes    | 93.69%                 | `-PE -PP -PS80,443,3389 -PU161,40125 -PA21 --source-port 53` |

# Port Scanning

A ferramenta também é capaz de realizar uma série de métodos de port scanning. Um port scanning é o processo de testar inúmeras portas de um host para verificar o estado em que elas se encontram. O estados reconhecidos pelo `nmap` são:

- **`open`**: uma aplicação está ativamente aceitando conexões [[5. TCP]] ou respondendo à pacotes [[5. UDP]].
- **`closed`**: não há nenhuma aplicação escutando pacotes nessa porta, contudo ela é acessível, pois está respondendo com pacotes de erro (`tcp reset`, `icmp port unreachable` etc).
- **`filtered`**: a ferramenta é incapaz de determinar se a porta está aberta, pois não há resposta para os pacotes enviados. Isso pode acontecer devido a configurações de [[5. Firewall]].
- **`unfiltered`**: a ferramenta consegue dizer que a porta é acessível, mas não consegue determinar se está aberta ou fechada. 
- **`open|filtered`**: quando não é possível determinar se a porta está aberta ou filtrada. Acontece com tipos de scanning em que portas abertas não retornam nenhuma resposta, tipo [[#UDP Scan]].
- **`closed|filtered`**: quando `nmap` é incapaz de determinar se a porta está fechada ou filtrada. Acontece apenas com o tipo de scanning [[#TCP Idle Scan]].

A forma mais simples de realizar um port scan com o `nmap` é:

```shell
$ nmap -Pn -p[ports] [hosts]
# -p: portas separadas por virgula ou range no formato <start>-<end> ou combinação dos dois, ex: 21-23,80,443
# -Pn: Desabilita "ping scanning". Isso é útil caso os hosts ativos já tenham sido mapeados na etapa de "Host Discovery"
# <host>: hostname ou endereço ip do alvo
```
## Técnicas de Port Scanning

O `nmap` permite especificar o tipo de scan que será realizado no alvo. Isso é importante, pois cada técnica implementa níveis de detecção e visibilidade diferentes. O tipo de varredura (scanning) de porta pode ser especificado, também, pelo parâmetro `-s`:

> [!info] Combinando técnicas
> Note que não há técnica que funcione como uma bala de prata, portanto é importante combinar execuções dependendo do cenário de pentest em que você se encontra. Isso só será possível se você conhecer as especificações de cada uma, como funcionam e quais cenários elas operam bem ou mal.
> 
> Entender cada técnica vai lhe ajudar a refinar os tipos de scanning que serão executados num host.


### TCP Syn Scan
[source](https://nmap.org/book/synscan.html)

```shell
$ nmap -Pn -p [ports] -sS [host]
```

A opção `-sS` faz com que o `nmap` inicie uma conexão TCP, mas não conclua o **3-Way Handshake**. A ferramenta envia um pacote com a flag `SYN` e, em caso do servidor responder com um `SYN/ACK`, devolve um `RST` para abortar a conexão.

Esse tipo de scanning é rápido, pois não completa o 3WHS e consequentemente não precisa encerrar a conexão. Além disso é bastante furtivo, pois não aparece nos logs como uma conexão típica. Como a conexão não é estabelecida, regras de [[5. Firewall]] que monitoram apenas a quantidade de conexões estabelecidas num curto período de tempo não vão conseguir identificar o host de origem. Contudo, **IDS** atuais são bastante capazes de detectar esse tipo de scan.
#### Tipos de resposta
| Resposta                                              | Estado     |
| ----------------------------------------------------- | ---------- |
| Resposta com pacote TCP SYN/ACK                       | `open`     |
| Resposta com pacote TCP RST                           | `closed`   |
| Nenhuma resposta (mesmo com retransmissão)            | `filtered` |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, or 13) | `filtered` |

> [!warning] Não funciona com proxies
> Esse tipo de scanning não funciona com [[5. Proxy|proxies]], pois o `nmap` constrói um **raw packet** ao invés de utilizar as APIs do sistema operacional. Devido a isso, ferramentas de proxy, por exemplo [[1. proxychains]], não conseguem interceptar os pacotes e redirecioná-los ao proxy.

> [!blueteam] Monitoramento de **Syn Scans** #blueteam 
> É possível configurar o Firewall para monitorar **Syn Scans**, por exemplo, ao criar uma regra no [[1. iptables]] com os módulos `recent` ou `limit`. Com estes módulos é possível fazer contagem ou limitação de pacotes com flag `SYN` originados de um mesmo host e direcioná-los para um [[1. iptables#Target|target]] específico

### TCP Connect Scan
[source](https://nmap.org/book/scan-methods-connect-scan.html)

```shell
$ nmap -Pn -p [ports] -sT [host]
```

A opção `-sT` faz com que o `nmap` realize uma tentativa completa de conexão TCP, ou seja, concluindo o **3-Way Handshake**. Esse tipo de técnica **não** é furtiva, porém é útil em alguns cenários em que é necessário se passar por uma tentativa real de conexão.
#### Tipos de resposta
| Resposta                                           | Estado     |
| -------------------------------------------------- | ---------- |
| Resposta com pacote TCP SYN/ACK                    | `open`     |
| Resposta com pacote TCP RST                        | `closed`   |
| Nenhuma resposta (mesmo com retransmissão)         | `filtered` |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, 13) | `filtered` |

> [!redteam] TCP Scan + Proxy #redteam 
> Como um **TCP Scan** realiza o **3-way handshake** completo, utilizando chamadas do sistema como a `connect` no Linux, ele pode ser executado através de **proxies**. Isso permite realizar varreduras mantendo o anonimato do IP de origem e pode ajudar a evitar firewalls baseados em IP, já que o tráfego parecerá legítimo e virá do proxy.

> [!blueteam] Monitorando **TCP Scans** #blueteam 
> Por ser uma técnica de scan bem barulhenta, é fácil monitorar **TCP Scans**. Para isso, basta escrever uma regra no [[1. iptables]] que limite ou a quantidade de tentativas de conexões ou quantidade de conexões estabelecidas/parelelas.

### UDP Scan 
[source](https://nmap.org/book/scan-methods-udp-scan.html)

```shell
$ nmap -Pn -p [ports] -sU [host]
```

A opção `-sU` ativa o modo de `UDP Scan`. Para a maioria das portas, o `nmap` envia um pacote vazio, contudo para as portas mais conhecidas (53, 67 etc) um payload específico para o protocolo será enviado.

#### Tipos de resposta
| Resposta                                                      | Estado          |
| ------------------------------------------------------------- | --------------- |
| Qualquer resposta com pacote UDP (pouco comum)                | `open`          |
| Nenhuma resposta (mesmo após outras tentativas)               | `open/filtered` |
| ICMP unreachable (type 3, code 3)                             | `closed`        |
| Outro erro ICMP unreachable (type 3, code 1, 2, 9, 10, ou 13) | `filtered`      |
#### Ambiguidade do estado `open|filtered`

Essa técnica de scanning sofre de um problema significativo: serviços ativos numa porta **UDP** raramente respondem pacotes com payload vazio. Para contornar isso, `nmap` envia pacotes específicos para as portas mais conhecidas, como tentativa de obter alguma resposta. Por isso existe o estado `open|filtered`, pois o `nmap` é incapaz de determinar se a porta está aberta ou filtrada.

Uma tentativa de resolver essa ambiguidade é usar o submódulo de detecção de versões `-sV`. Basicamente o `nmap` envia **probes** personalizados para portas marcadas como `open|filtered` para provocar alguma resposta; isso é pouco **stealth**, pois gera bastante tráfego. Esse submódulo é bem complexo e vale a pena dar uma lida na [fonte](https://nmap.org/book/vscan.html).


> [!redteam] Cuidado com o `-sV` #redteam 
> Ativar o submódulo de detecção de versões para contornar a ambiguidade de portas `open|filtered` pode ser problemático devido ao "barulho" que ele gera na rede. O tráfego de pacotes pode aumentar bastante, devido à múltiplas tentativas e tamanho dos payloads personalizados enviados pelo `nmap`.

> [!blueteam] Configure sistemas de **IDS/IPS** #blueteam 
> Sistemas de detecção e prevenção de intrusão ([[5. IDS]]/[[5. IPS]]) são uma ótima maneira de detectar scannings, ainda mais os que são bastante barulhentos.

#### Lentidão no scanning UDP
 
A única forma de determinar se uma porta está fechada é caso o `nmap` receba um pacote ICMP do host alvo. Muitos sistemas possuem **rate limit**  para pacotes ICMP, limitando o número de respostas por segundo. Como o `nmap` necessita dessas respostas, o scan se torna muito lento devido à quantidade de tentativas feitas. Isso pode tentar ser contornado com as seguintes opções:
- `--top-ports` ou `-p` para limitar o número de portas scaneadas.
- `--scan-delay` para aumentar o delay entre cada teste, para evitar "triggar" o rate limit do servidor.
-  `--max-retries` ou `--host-timeout` para ajustar número de tentativas e timeout 

> [!redteam] UDP como superfície de ataque frequentemente ignorada #redteam
> Serviços UDP raramente são auditados com a mesma profundidade que TCP. Portas UDP comuns e seus riscos associados:
> - `53` (DNS): zone transfer, cache poisoning, amplification attacks
> - `161/162` (SNMP): enumeração de informações de sistema com community strings padrão (`public`/`private`)
> - `67/68` (DHCP): DHCP starvation, rogue DHCP server
> - `69` (TFTP): acesso sem autenticação a arquivos de configuração
> - `2049` (NFS): montagem de compartilhamentos sem autenticação
> - `500` (IKE/IPSec): fingerprinting de implementações de VPN


### FIN, NULL e Xmas Scan
[source](https://nmap.org/book/scan-methods-null-fin-xmas-scan.html)

Esses três tipos de scan exploram sistemas que estão em conformidade com a [RFC do protocolo TCP](https://www.rfc-editor.org/rfc/rfc793.txt). A exploração consiste no entendimento de dois requisitos importantes:
1. A RFC diz que se a porta do host estiver **fechada** e um pacote TCP enviado à ela não conter a flag `RST`, então o host deve responder com um `RST`. (*p 65, SEGMENT ARRIVES - If the state is CLOSED then...*)
2. A RFC diz que se a porta do host estiver **aberta** e um pacote TCP enviado à ela não conter a flag `SYN` ou `RST` ou `ACK`, então o host deve ignorar o pacote silenciosamente e não responder nada. (*p 66,  SEGMENT ARRIVES - If the state is LISTEN then... fourth other text or control*)

A partir deste dois requisitos conseguimos concluir que:
- Qualquer porta que esteja **fechada** e receber um pacote que **não** possua a flag `RST` responderá com um `RST`, justamente para indicar que a porta está fechada.
- Pacotes enviados sem a flag `SYN`, `RST` ou `ACK` para portas **abertas** não serão respondidos. Dessa forma, a porta está ou `open` ou `filtered`.

Há três jeitos de correspondermos aos requisitos estabelecidos pela RFC, resultando, portanto, em três tipos de scan:
1. `-sN`: **Null Scan**, consiste em mandar o cabeçalho `flags` zerado.
2. `-sF`: **FIN Scan**, consiste em mandar apenas a flag `FIN`.
3. `-sX`: **Xmas Scan**, consistem em mandar as flags `FIN`, `PSH` e `URG`.

Este tipo de scanning obviamente não funciona com portas **UDP**.
#### Tipos de resposta
| Resposta                                              | Estado          |
| ----------------------------------------------------- | --------------- |
| Nenhuma resposta (mesmo após outras tentativas)       | `open/filtered` |
| Resposta com TCP RST                                  | `closed`        |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, or 13) | `filtered`      |

> [!redteam] Conformidade com RFC #redteam 
> A maioria de hosts UNIX-like estão em conformidade com a RFC, dessa forma, essas técnicas de scan podem ser bem aproveitadas contra esse tipo de sistema. O comportamento pode ser testado, inclusive, com o [[1. hping3]] + servidor apache:
> ```shell
> $ hping3 -n 1 -p 80 -F [host]
> ```
> Se a porta estiver `closed`, como não estamos enviando a flag `RST`, então o host provavelmente vai nos retornar um `RST`. Se a porta estiver `open`, como não estamos enviando a flag `SYN` para iniciar uma conexão, então o host irá ignorar o pacote silenciosamente. O mesmo comportamento ocorre enviando nenhuma flag ou enviando as flags `FIN`, `PSH` e `URG` simultaneamente.

> [!redteam] Como lidar com `open|filtered` #redteam 
> Caso o host possua uma regra de [[5. Firewall]] para dropar pacotes na porta de destino, um **FIN/NULL/Xmas** scan identificará que a porta está `open|filtered`. Isso pode ser testado ao criar a seguinte regra no [[1. iptables]] e depois rodar o `nmap`:
> ```shell
> $ iptables -A INPUT -p tcp --dport 80 -j DROP
> ```
> Por este motivo é importante combinar diferentes tipos de scanning. Neste caso, [[#ACK Scan]] pode ser útil se executado após identificar portas `open|filtered`.

> [!warning] Ineficaz contra Windows
> A maioria das implementações do Windows **não** segue esta parte da RFC, em vez disso respondem com `RST` para qualquer pacote recebido em qualquer porta, independentemente se a porta esta aberta ou fechada. O resultado é que todas as portas retornam como `closed` num **FIN/NULL/Xmas** scan contra Windows, tornando a técnica completamente inútil nesse sistema operacional.

### ACK Scan
[source](https://nmap.org/book/scan-methods-ack-scan.html)

Tipo de scan focado em detectar regras de Firewall. Consiste em enviar um raw packet TCP apenas com a flag `ACK`. Portas que estiverem abertas ou fechadas responderão com `RST` a não ser que estejam sendo filtradas por um Firewall. Este tipo de filtragem obviamente não funciona com portas **UDP**. 
#### Tipos de resposta
| Resposta                                              | Estado       |
| ----------------------------------------------------- | ------------ |
| Resposta com TCP RST                                  | `unfiltered` |
| Nenhuma resposta (mesmo após outras tentativas)       | `filtered`   |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, or 13) | `filtered`   |

> [!info] Desambiguar `open|filtered` com **ACK Scan**
> Esse tipo de scan é útil para tentar desambiguar portas que foram identificadas como `open|filtered` por outras técnicas de scanning. Por exemplo, se uma porta scaneada com [[#FIN, NULL e Xmas Scan|FIN Scan]] retornar `open|filtered`, mas num **ACK Scan** retornar como `unfiltered` (que significa `open` ou `closed`), então logicamente essa porta só pode estar `open`.
> 

> [!redteam] Trabalhoso para ser filtrado #redteam 
> Raw packets contendo apenas a flag `ACK` são comuns em conexões TCP legítimas, pois são usados para confirmar recebimento de dados. Contudo, esse tipo de pacote não indica qual [[5. Host]] iniciou a conexão, dessa forma, é difícil para [[5. Firewall#Stateless Firewall|Firewalls Stateless]] identificarem se é um pacote legítimo ou não.

> [!blueteam] Stateful Firewalls #blueteam 
> [[5. Firewall#Stateful Firewall|Stateful Firewalls]], por manterem uma tabela de conexões  abertas, conseguem identificar raw packets `ACK` ilegítimos. A desvantagem é que esse tipo de firewall consome muitos recursos da máquina e podem sofrer ataques [[7. Denial of Service|DoS]] por table exhaustion. Além disso podem impactar a velocidade do tráfego de pacotes devido ao overhead para verificar se a conexão existe.

# NSE (Nmap Script Engine)
[source](https://nmap.org/book/nse.html)

O **Nmap Script Engine** é uma funcionalidade disponibilizada pelo `nmap` para a criação e execução de scripts em `Lua` visando automatizar uma variedade de scannings em um host alvo, seja: detecção e enumeração de hosts e serviços, bruteforce, análise de vulnerabilidades e até mesmo exploração de exploits. Arquivos de scripts **NSE** são terminados com a extensão `.nse`.

## Categorias

As categorias de scripts **NSE** estão listadas em [NSE - Script Categories](https://nmap.org/book/nse-usage.html#nse-categories) no site oficial do Nmap, e incluem: `auth`, `broadcast`, `brute`, `default`, `discovery`, `dos`, `exploit`, `external`, `fuzzer`, `intrusive`, `malware`, `safe`, `version` e `vuln`.

Cada categoria representa um conjunto de scripts agrupados por finalidade específica, facilitando a seleção conforme o objetivo do scan. Um único script pode ser classificado em múltiplas categorias simultaneamente, refletindo sua aplicabilidade em diferentes cenários de enumeração, detecção ou exploração.

## Diretório de scripts

Por padrão, os scripts são armazenados no diretório `/usr/share/nmap/scripts`. Tudo o que se refere à script é terminado com a extensão `.nse`. Há também o arquivo `script.db`, que é uma espécie de "banco de dados" que lista todos os scripts e suas categorias. Uma entrada no arquivo `script.db` é algo como o mostrado abaixo:

```
Entry { filename = "some-script.nse", categories = { "discovery", "version", } }
```

Dessa forma, é possível buscar scripts com nomes e categorias específicas usando [[1. grep]]: 

```shell
$ grep -E '("vuln"|"exploit")' script.db
# Entry { filename = "dns-update.nse", categories = { "intrusive", "vuln", } }
# Entry { filename = "clamav-exec.nse", categories = { "exploit", "vuln", } }

$ grep "smb" script.db
# Entry { filename = "smb-brute.nse", categories = { "brute", "intrusive", } }
# Entry { filename = "smb-double-pulsar-backdoor.nse", categories = { "malware", "safe", "vuln", } }
```

## Detalhes sobre um script

Na dúvida sobre o que um script faz e quais suas categorias, é possível usar a opção `--script-help` para buscar por informações:

```shell
$ nmap --script-help "ssh-auth-methods"
# Starting Nmap 7.95 ( https://nmap.org ) at 2025-11-24 20:08 -03
#
# ssh-auth-methods
# Categories: auth intrusive
# https://nmap.org/nsedoc/scripts/ssh-auth-methods.html
#   Returns authentication methods that a SSH server supports.
#
#   This is in the "intrusive" category because it starts an
#   authentication with a username which may be invalid. The abandoned
#   connection will likely be logged.
```

Note que o argumento passado para `--script-help` pode receber expressões avançadas como `--script-help "ssh-* and discovery"`. Mais detalhes sobre expressões, ver [[#NSE (Nmap Script Engine)#Seleção avançada de scripts|NSE - Seleção avançada de scripts]].

## Execução

A opção `--script` define qual ou quais scripts NSE serão executados durante o scan. Ela permite especificar múltiplos scripts simultaneamente, utilizando uma lista separada por vírgulas que pode incluir `filename`, `category` ou `directory`, ou mesmo combinações entre esses três tipos.

- `filename`: nome do script; a extensão pode ser omitida e é possível especificar o caractere `*` para selecionar todos os scripts que comecem com um determinado prefixo, ex: `http-*`.
- `category`: alguma das categorias citadas na seção [[#NSE (Nmap Script Engine)|NSE - Categorias]].
- `directory`: um diretório absoluto ou relativo contendo scripts `nse`; todos os scripts do diretório serão executados.

No exemplo abaixo, o script de nome `ssh-brute` e todos os scripts sob a categoria `auth` serão executados no serviço de porta `22` do host `172.16.1.50`:

```shell
$ nmap -n -Pn --script="ssh-brute,auth" -p22 172.16.1.50
# PORT   STATE SERVICE
# 22/tcp open  ssh
# | ssh-auth-methods: 
# |   Supported authentication methods: 
# |     publickey
# |_    password
# | ssh-publickey-acceptance: 
# |_  Accepted Public Keys: No public keys accepted
# | ssh-brute: 
# |   Accounts: No valid accounts found
# |_  Statistics: Performed 2 guesses in 24 seconds, average tps: 0.1
```

No retorno acima, junto com `ssh-brute` também foram executados os scripts `ssh-auth-methods` e `ssh-publickey-acceptance`, ambos de categoria `auth`.

O seletor de scripts, além de receber `filename`, `category` e `directory`, também é capaz de interpretar expressões complexas. Para mais detalhes, ver [[#NSE (Nmap Script Engine)#Seleção avançada de scripts|NSE - Seleção avançada de scripts]].

> [!info] Categoria de scripts padrão
> A opção `-sC` (ou `--script=default`) executa todos os scripts da categoria `default`. Para listar quais são esses scripts, basta executar o comando abaixo:
> 
> ```shell
> $ grep '"default"' /usr/share/nmap/scripts/script.db
> ```
> 
> Alguns desses scripts são intrusivos, então é bom tomar cuidado com esta execução.

> [!tip] Execução otimizada de scripts
> Lembrando que o **NSE** não é uma funcionalidade a parte do `nmap`, mas sim trabalha em conjunto com as demais funcionalidades já abordadas como [[#Port Scanning]] e [[#Host Discovery]]. Dessa forma, é altamente recomendado a leitura da seção [[#Técnicas de otimização]] para extrair o melhor possível dos scripts, seja no que se refere à velocidade de execução até qualidade dos resultados obtidos.

### Passagem de argumentos

Alguns scripts permitem a passagem de argumentos para controlar seu comportamento durante a execução, incluindo parâmetros como timeout, pares de usuário e senha, número de tentativas, ajuste de verbosidade, definição de chaves ou tokens, entre muitos outros. 

Os argumentos são estruturados como pares de `key=value` e devem ser especificados pela opção `--script-args`. É possível informar múltiplos argumentos passando uma lista separada por vírgula:

```shell
$ nmap \
	--script=smb-enum-users.nse \
	--script-args="smbusername=admin,smbpassword=123456" \
	-p 445 \
	[host]
```

Caso esteja executando múltiplos scripts que compartilham argumentos de mesmo nome, é possível especificar o namespace a qual o argumento faz parte, prefixando o nome do script:

```shell
$ nmap \
	--script=script-a,scrip-b \
	--script-args="script-a.timeout=100,script-b.timeout=200" \
	...
```


## Seleção avançada de scripts

Além da simples especificação de `filename`, `category` e `directory` ao referenciar scripts, há também um dialeto de expressões mais complexas que envolvem uso de operadores booleanos, entre eles:

- **`or`**:  `--script="safe or auth"`, `--script="smb-enum-users or `; comportamento similar ao uso de lista separada por virgula
- **`and`**: `--script="vuln and exploit"`; usado com categorias para filtrar scripts  que correspondem a um conjunto especifico de categorias.
- **`not`**: `--script="not intrusive"`, `--script="not http-*"`; nega a expressão posterior.

Os operadores podem ser combinados, para então formar expressões compostas. Inclusive, é possível o uso de expressões entre `( )` para definir precedência:

```shell
$ nmap \
    -n -Pn -sV -p22,2222 \
	--script="ssh-* and (not dos) and ( version or auth )" \
	172.16.1.50
```

No exemplo acima, a expressão executará apenas os scripts que voltados à ssh (`ssh-*`), que não causem [[7. Denial of Service|DoS]] (`not dos`) e que sejam ou para detecção de versão ou relacionados a autenticação (`version or auth`).

> [!note] Expressões com `--script-help`
> Note que esta seleção avançada de scripts também funciona com a opção `--script-help` para busca e detalhes de scripts.

# Técnicas de otimização

O **NSE** não é uma funcionalidade a parte do `nmap`, mas sim trabalha em conjunto com as demais funcionalidades já citadas, como [[#Port Scanning]] e [[#Host Discovery]]. Dessa forma, ao executar um script, é necessário tomar o cuidado com quais hosts, portas e métodos de scanning e descobrimento a ferramenta trabalhará.

As funcionalidades já abordadas do `nmap`, como [[#Host Discovery]], [[#Port Scanning]] e [[#NSE (Nmap Script Engine)]], não trabalham de forma isoladas uma das outras, mas sim em conjunto se complementando. Dessa forma, ao executar um scanning, é necessário tomar cuidado com quais hosts, portas e métodos com os quais a ferramenta trabalhará.

Por exemplo, a execução abaixo:

```shell
$ nmap --script=ssh-brute 172.16.1.50
```

fará não apenas **Host Discovery** de `172.168.1.50`, mas também [[6. Resolução Reversa de DNS]], **Port Scanning** do tipo [[#TCP Syn Scan]] (ou [[#TCP Connect Scan]], dependendo das permissões) para as top 1000 portas TCP e, por fim, a execução de scripts automatizados.

Com isso, é possível perceber que, dependendo da situação, a execução acima pode ser otimizada de múltiplas maneiras.

## Omitir Host Discovery (Ping Scanning)

Supondo que já seja conhecida a disponibilidade do host alvo, podemos omitir qualquer técnica de [[#Host Discovery]] (ou Ping Scanning). Isso é alcançado com a opção `-Pn`:

```shell
$ nmap -Pn --script=ssh-brute 172.16.1.50
```

## Omitir resolução reversa de DNS

A resolução reversa de DNS é útil em cenários em que, a partir de um endereço IP, queremos descobrir o nome do domínio; isso é feito ao consultar os [[6. Resolução Reversa de DNS|registros PTR]]. Contudo, nem sempre isso é desejado e como o `nmap` realiza essa verificação por padrão, podemos apenas omiti-la com a opção `-n`:

```shell
$ nmap -n --script=ssh-brute 172.16.1.50
```

## Omitir Port Scanning

Caso o `nmap` esteja sendo utilizado para, por exemplo, detectar hosts disponíveis numa rede, não convém realizar um port scanning, portanto podemos omitir essa funcionalidade da execução com a opção `-sn`:

```shell
$ nmap -sn --script=address-info 172.16.1.0/24
$ nmap -sn 172.16.1.50
```

> [!note] `-sn` não omite todos os port scannings
> Há um mínimo necessário para detectar a disponibilidade de um host. Isso acontece, pois uma das técnicas utilizadas é um [[#TCP Syn Scan]] na porta `tcp/443` e um [[#ACK Scan]] na porta `tcp/80` devido a alta probabilidade de ter algum serviço HTTP em execução, além da baixa probabilidade de bloqueio de firewall.

## Especificar portas

Após a detecção de serviços ativos no host alvo, é muito importante fazer enumeração para identificar o vendor e versões ou até mesmo testar scripts para detecção de vulnerabilidades. Neste caso, faz sentido especificarmos quais são as portas que desejamos focar o scanning e isso pode ser feito com a já conhecida opção `-p`:

```shell
$ nmap -p22,2222 --script=ssh-brute 172.16.1.50
```

## Combinações de técnicas

Das técnicas abordadas acima, muitas podem ser combinadas para extrairmos a melhor execução possível do scanning:

```shell
$ nmap -n -Pn -p22,2222 --script=ssh-brute 172.16.1.50
```

Neste exemplo, tanto o **Host Discovery** quanto **Reverse DNS** serão omitidos, além de que o scanning de portas será executado apenas para as portas `22` e `2222` que, por fim, caso estejam abertas, será executado o script `ssh-brute`.

# OS & Services Detection
[source](https://nmap.org/book/man-version-detection.html)

O `nmap` oferece capacidades de detecção de versão de serviços e de sistema operacional do host alvo. Essas funcionalidades são fundamentais para identificar vetores de ataque específicos, como versões desatualizadas de serviços com vulnerabilidades conhecidas.

## Detecção de Versão de Serviços (`-sV`)
[source](https://nmap.org/book/vscan.html)

```shell
$ nmap -Pn -sV -p [ports] [host]
```

A opção `-sV` ativa a detecção de versão de serviços. O `nmap` envia uma série de pacotes para cada porta aberta e compara as respostas com seu banco de dados `nmap-service-probes`, tentando identificar o serviço em execução, o vendor e a versão.

O resultado de uma porta com `-sV` é enriquecido com `SERVICE`, `VERSION` e outros campos:

```
PORT    STATE SERVICE VERSION
22/tcp  open  ssh     OpenSSH 8.9p1 Ubuntu 3ubuntu0.6 (Ubuntu Linux; protocol 2.0)
80/tcp  open  http    Apache httpd 2.4.52 ((Ubuntu))
443/tcp open  ssl/http nginx 1.18.0 (Ubuntu)
```

### `--version-intensity`

O parâmetro `--version-intensity [0-9]` (padrão `7`) controla quão agressivamente o `nmap` tenta identificar a versão. Valores mais baixos enviam apenas os pacotes mais prováveis; valores mais altos enviam todos os pacotes disponíveis, aumentando a precisão mas também o tráfego gerado.

- `--version-light`: equivalente a `--version-intensity 2`; rápido, mas menos preciso.
- `--version-all`: equivalente a `--version-intensity 9`; tenta todos os pacotes disponíveis.

> [!redteam] Barulho gerado pelo `-sV` #redteam
> A detecção de versão gera um volume de tráfego significativamente maior que um port scan simples. Em situações em que é necessário furtividade, é preferível combinar `--version-intensity` baixo com timing lento e limitar as portas alvo com `-p`. Usar `-sV` sem saber o que está fazendo pode gerar alertas em [[5. IDS]]/[[5. IPS]].

> [!blueteam] Supressão de banners #blueteam
> Uma das formas mais simples de dificultar a detecção de versão é suprimir ou falsificar os banners expostos pelos serviços. Exemplos:
> - **Apache**: `ServerTokens Prod` e `ServerSignature Off` no `httpd.conf` ocultam versão e OS.
> - **OpenSSH**: `DebianBanner no` no `sshd_config` (Debian/Ubuntu) remove a versão do banner.
> - **Nginx**: `server_tokens off` no bloco `http {}`.
>
> Isso não impede a detecção, mas obriga o atacante a depender de pacotes mais intrusivos e que levantam suspeita mais facilmente.

## Detecção de Sistema Operacional (`-O`)
[source](https://nmap.org/book/man-os-detection.html)

```shell
$ nmap -Pn -O -p [ports] [host]
```

A opção `-O` ativa o fingerprinting de sistema operacional. O `nmap` envia uma série de probes TCP, UDP e ICMP e analisa as respostas (tamanho de janela TCP, TTL, flags, comportamento ICMP etc) para comparar com seu banco de dados `nmap-os-db` e determinar o SO do alvo.

```
OS details: Linux 5.15 - 5.19
Network Distance: 1 hop
```

> [!warning] Requisito para detecção de OS
> A detecção de OS requer ao menos uma porta aberta e uma porta fechada no host alvo. Sem ambas, o `nmap` não consegue construir o perfil de fingerprinting e reportará `OS details: Unknown`. Caso isso ocorra, tente especificar uma faixa maior de portas com `--top-ports` (ou `-p`) ou verificar se alguma porta fechada está acessível.

> [!redteam] Melhorando a precisão #redteam
> Em casos em que o `nmap` retorna múltiplos candidatos de OS ou reporta baixa confiança, a opção `--osscan-guess` (ou `--fuzzy`) faz com que ele imprima o candidato mais próximo mesmo sem alta certeza. Combinar `-O` com `-sV` também melhora a precisão, pois versões de serviços detectadas ajudam a confirmar o SO inferido.
> ```shell
> $ nmap -Pn -O --osscan-guess -sV -p22,80,443 [host]
> ```

> [!blueteam] Proteção contra OS fingerprinting #blueteam
> [[5. IPS|IPSs]] e ferramentas como `scrubber` (OpenBSD) ou o módulo `NFQUEUE` do `iptables` podem normalizar respostas TCP/IP, eliminando as peculiaridades que o `nmap` usa para identificar o SO.

## Combinando detecções (`-A`)

```shell
$ nmap -Pn -A -p [ports] [host]
```

A opção `-A` é um atalho que combina `-sV` (detecção de versão) + `-O` (detecção de OS) + `-sC` (scripts da categoria `default`, ver [[#NSE (Nmap Script Engine)]]) + `--traceroute`. É a opção mais completa para reconhecimento de um host, mas também a mais ruidosa.

> [!redteam] `-A` é agressivo #redteam
> O uso de `-A` deve ser evitado em cenários que exigem furtividade. É preferível compor manualmente as opções necessárias (`-sV --version-intensity 3 -O`) para ter mais controle sobre o que é enviado.


# Evasão de mecanismos de segurança

Tentativas de **host discovery** e **port scanning** podem ser facilmente frustradas por mecanismos de segurança como [[5. IPS]]s ou honeypots ativos. Esses tipos de ferramentas têm como objetivo identificar tráfego suspeito na rede para rejeitar pacotes e até mesmo, em casos mais restritos, bloquear [[5. IP (Address)|IP]]. Contudo, há formas de contornar ou minimizar esse tipo de bloqueio.

## Decoy

Decoy é uma técnica de evasão em que o atacante envia pacotes forjados com endereços IP de origem falsos, além do seu próprio. O objetivo é confundir os mecanismos de segurança, como [[5. IDS]], [[5. IPS]] ou sistemas de log, fazendo parecer que o scan está sendo realizado por múltiplos IPs simultaneamente.

Essa técnica pode ser empregada ao utilizar a opção `-D` do `nmap`:

```shell
$ nmap -D 172.16.1.50,192.168.0.10,1.1.1.1 -sS --top-ports=1000 [target]
```

No exemplo acima, junto com pacotes contendo seu IP original, serão enviados mais três pacotes contendo os IPs "falsos".

> [!tip] Aleatorizar IPs
> É possível aleatorizar os IPs  com a opção `-D RND:<number>`, que faz com que o `nmap` gere a quantidade de endereços IP especificadas em `<number>`.

> [!redteam] Cuidado com hosts inativos
> Especificar hosts inativos como decoy pode ser um problema, pois se torna fácil identificar qual o IP real do atacante. Por exemplo, na técnica [[#TCP Syn Scan]], o host atacante não conclui o 3WHS, pois envia um `RST` para o alvo. Hosts que estão inativos não enviam pacote algum, portanto o atacante só pode ser aquele que retornou alguma resposta, seja ela um `RST` ou até mesmo um `SYN/ACK`.
> 
> **Além disso, utilizar hosts inativos pode caracterizar seu scan como um Syn Flood, um tipo de ataque [[7. Denial of Service|DDoS]].**

> [!blueteam] Lidar com decoys
> Por mais que scannings que utilizem decoys inundem arquivos de log, é possível identificar alguns padrões. Por exemplo, geralmente todos os IPs(falsos + real) envolvidos no ataque enviam pacotes para as mesmas portas durante um curto período de tempo. Além disso, é possível que os IPs forjados utilizados como decoy não respondam aos pacotes, tornando-se fácil identificar qual host respondeu, portanto, o host atacante real.

## Fragmentação de Pacotes (`-f` / `--mtu`)
[source](https://nmap.org/book/man-bypass-firewalls-ids.html)

A fragmentação consiste em dividir os pacotes enviados em fragmentos menores, dificultando que sistemas de inspeção de pacotes, como [[5. IDS]], [[5. IPS]] ou firewalls com inspeção superficial, consigam remontar e inspecionar o conteúdo completo.

```shell
$ nmap -f -sS -p [ports] [host]        # fragmentos de 8 bytes
$ nmap -ff -sS -p [ports] [host]       # fragmentos de 16 bytes
$ nmap --mtu 24 -sS -p [ports] [host]  # fragmentos de tamanho customizado (múltiplo de 8)
```

- `-f`: divide os cabeçalhos TCP/UDP em fragmentos de **8 bytes**.
- `-ff`: fragmentos de **16 bytes**.
- `--mtu [size]`: define o tamanho máximo de cada fragmento; deve ser múltiplo de 8.

> [!redteam] Limitações da fragmentação #redteam
> A maioria dos firewalls e IDS modernos realiza **reassembly** de fragmentos antes da inspeção, tornando essa técnica ineficaz contra sistemas como `iptables` com `nf_conntrack` ou [[1. snort]] com o preprocessador de stream. A fragmentação é mais eficaz contra appliances legados ou configurações de firewall stateless. Combinar com `--data-length` e timing lento aumenta as chances de evasão.

> [!blueteam] Detecção de fragmentação anômala #blueteam
> Pacotes TCP excessivamente fragmentados são raros em tráfego legítimo. O Snort possui regras específicas para alertar sobre fragmentação agressiva. No `iptables`, é possível descartar fragmentos com:
> ```shell
> $ iptables -A INPUT -f -j DROP
> ```
> Porém, isso pode quebrar tráfego legítimo fragmentado por MTU de rede; avalie o ambiente antes de aplicar.

## Timing e Velocidade (`-T`)
[source](https://nmap.org/book/man-performance.html)

O `nmap` possui seis modos de timing que controlam a velocidade e agressividade do scan. São especificados com `-T[0-5]`:

| Template | Nome     | Descrição                                                                                            |
| -------- | -------- | ---------------------------------------------------------------------------------------------------- |
| `-T0`    | Paranoid | Envia um probe por vez com delay de 5 minutos entre cada um. Extremamente lento, máxima furtividade. |
| `-T1`    | Sneaky   | Delay de 15 segundos entre probes. Projetado para evadir a maioria dos IDS.                         |
| `-T2`    | Polite   | Delay de 0.4 segundos. Reduz o impacto na largura de banda do alvo.                                 |
| `-T3`    | Normal   | Comportamento padrão do `nmap`; paralelismo adaptativo.                                              |
| `-T4`    | Aggressive | Assume rede rápida e confiável; reduz timeouts e aumenta paralelismo. Recomendado em LANs.         |
| `-T5`    | Insane   | Velocidade máxima; sacrifica precisão. Pode perder portas abertas em redes lentas.                  |

### Parâmetros individuais de timing

É possível configurar os parâmetros de timing individualmente, para mais controle além dos modos pré definidos:

- `--min-rate [n]` / `--max-rate [n]`: limites mínimo e máximo de pacotes por segundo enviados.
- `--scan-delay [time]` / `--max-scan-delay [time]`: delay mínimo e máximo entre probes para um mesmo host.
- `--min-parallelism [n]` / `--max-parallelism [n]`: número mínimo e máximo de probes paralelos.
- `--host-timeout [time]`: abandona um host que não respondeu no tempo especificado.
- `--max-retries [n]`: número máximo de retransmissões de um probe (padrão `10`).

> [!redteam] Furtividade com timing lento #redteam
> `-T0` e `-T1` tornam o tráfego do scan indistinguível de conexões legítimas esporádicas, especialmente quando combinados com `--randomize-hosts` (ver [[#Aleatorizar Hosts (`--randomize-hosts`)]]) e `--source-port 53`.

> [!blueteam] Detecção baseada em correlação temporal #blueteam
> Scans lentos são o maior desafio para detecção baseada em volume. A defesa mais eficaz é correlação temporal com janela de tempo longa: ferramentas como [[1. snort]] com o preprocessador `sfPortscan`, [[1. portsentry]] ou SIEMs configurados para correlacionar eventos de múltiplas sessões ao longo de horas conseguem identificar esse padrão. Logs de conexão centralizados (NetFlow/IPFIX) são essenciais para essa análise.

## Aleatorizar Hosts (`--randomize-hosts`)
[source](https://nmap.org/book/man-bypass-firewalls-ids.html)

```shell
$ nmap --randomize-hosts -sS -p [ports] [targets]
```

Por padrão, o `nmap` escaneia os hosts na ordem em que foram especificados (ou em ordem numérica de IP). A opção `--randomize-hosts` embaralha a ordem dos hosts antes de iniciar o scan, evitando que o padrão sequencial de IPs seja detectado como uma varredura de rede.

> [!redteam] Combinação com timing lento #redteam
> `--randomize-hosts` combinado com `-T1` ou `-T0` é altamente eficaz em redes grandes. Em vez de varrer `192.168.1.1, .2, .3...` sequencialmente, o scan pula entre IPs aleatórios com longos intervalos de tempo, tornando cada probe aparentemente independente.

## Spoof de Endereço MAC (`--spoof-mac`)
[source](https://nmap.org/book/man-bypass-firewalls-ids.html)

```shell
$ nmap --spoof-mac [MAC|vendor|0] -sS -p [ports] [host]
```

A opção `--spoof-mac` permite forjar o endereço MAC de origem dos pacotes enviados. Pode receber três tipos de argumento:

- **MAC literal**: ex: `--spoof-mac 00:11:22:33:44:55`
- **Vendor/fabricante**: ex: `--spoof-mac Apple`; o `nmap` gera um MAC aleatório com o OUI do vendor.
- **`0`**: gera um MAC completamente aleatório a cada execução.

> [!warning] Limitação a redes locais
> O spoofing de MAC só é eficaz em redes locais (**Layer 2**), pois endereços MAC não são roteados além do segmento de rede. Em ataques remotos via internet, o MAC de origem é irrelevante, pois é substituído a cada hop pelos roteadores intermediários.

> [!redteam] Escolha de vendor OUI #redteam
> Para máxima efetividade em redes locais, identifique previamente qual vendor de hardware é predominante na rede alvo (ex: todos os switches são Cisco, ou todos os hosts são Dell). Use `--spoof-mac [vendor]` para gerar um MAC compatível com o ambiente, reduzindo a chance de alertas em sistemas de monitoramento que fazem correlação de OUI com dispositivos cadastrados.
