O `nmap` é uma ferramenta de código aberto usada para descoberta de hosts e varredura de portas em redes. Ele permite identificar quais [[5. Host]]s estão ativos, quais portas estão abertas, quais serviços estão rodando e até o sistema operacional dos alvos.

# Port Scanning

A ferramenta também é capaz de realizar uma série de métodos de port scanning. Um port scanning é o processo de testar inúmeras portas de um host para verificar o estado em que elas se encontram. O estados reconhecidos pelo `nmap` são:
- `open`: uma aplicação está ativamente aceitando conexões [[5. TCP]] ou respondendo à pacotes [[5. UDP]].
- `closed`: não há nenhuma aplicação escutando pacotes nessa porta, contudo ela é acessível, pois está respondendo com pacotes de erro (`tcp reset`, `icmp port unreachable` etc).
- `filtered`: a ferramenta é incapaz de determinar se a porta está aberta, pois não há resposta para os pacotes enviados. Isso pode acontecer devido a configurações de [[5. Firewall]].
- `unfiltered`: a ferramenta consegue dizer que a porta é acessível, mas não consegue determinar se está aberta ou fechada. 
- `open|filtered`: quando não é possível determinar se a porta está aberta ou filtrada. Acontece com tipos de scanning em que portas abertas não retornam nenhuma resposta, tipo [[#UDP Scan]].
- `closed|filtered`: quando `nmap` é incapaz de determinar se a porta está fechada ou filtrada. Acontece apenas com o tipo de scanning [[#TCP Idle Scan]]. 

A forma mais simples de realizar um port scan com o `nmap` é:

```shell
$ nmap -p [ports] [host]
# -p: portas separadas por virgula ou range no formato <start>-<end> ou combinação dos dois, ex: 21-23,80,443
# <host>: hostname ou endereço ip do alvo
```
## Técnicas de Scan

O `nmap` permite especificar o tipo de scan que será realizado no alvo. Isso é importante, pois cada técnica implementa níveis de detecção e visibilidade diferentes. O tipo de varredura (scanning) de porta pode ser especificado, também, pelo parâmetro `-s`:

> [!info] Combinando técnicas
> Note que as técnicas apresentadas abaixo podem ser combinadas numa única execução de `nmap`, para que vários tipos de scanning sejam feitos simultaneamente.
### TCP Syn Scan
[source](https://nmap.org/book/synscan.html)

```shell
$ nmap -p [ports] -sS [host]
```

A opção `-sS` faz com que o `nmap` inicie uma conexão TCP, mas não conclua o **3-Way Handshake**. A ferramenta envia um pacote com a flag `SYN` e, em caso do servidor responder com um `SYN/ACK`, devolve um `RST` para abortar a conexão.

Esse tipo de scanning é rápido, pois não completa o 3WHS e consequentemente não precisa encerrar a conexão. Além disso é bastante furtivo, pois não aparece nos logs como uma conexão típica. Como a conexão não é estabelecida, regras de [[5. Firewall]] que monitoram apenas a quantidade de conexões estabelecidas num curto período de tempo não vão conseguir identificar o host de origem. Contudo, **IDS** atuais são bastante capazes de detectar esse tipo de scan.
#### Tipos de resposta
| Resposta                                              | Estado     |
| ----------------------------------------------------- | ---------- |
| Resposta com pacote TCP SYN/ACK                       | `open`     |
| Resposta com pacote TCP RST                           | `closed`   |
| Nenhuma resposta (mesmo com retransmissão)            | `filtered` |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, or 13) | `filtered` |

> [!warning] Não funciona com proxies
> Esse tipo de scanning não funciona com [[5. Proxy|proxies]], pois o `nmap` constrói um **raw packet** ao invés de utilizar as APIs do sistema operacional. Devido a isso, ferramentas de proxy, por exemplo [[1. proxychains]], não conseguem interceptar os pacotes e redirecioná-los ao proxy.

> [!blueteam] Monitoramento de **Syn Scans** #blueteam 
> É possível configurar o Firewall para monitorar **Syn Scans**, por exemplo, ao criar uma regra no [[1. iptables]] com os módulos `recent` ou `limit`. Com estes módulos é possível fazer contagem ou limitação de pacotes com flag `SYN` originados de um mesmo host e direcioná-los para um [[1. iptables#Target|target]] específico

### TCP Connect Scan
[source](https://nmap.org/book/scan-methods-connect-scan.html)

```shell
$ nmap -p [ports] -sT [host]
```

A opção `-sT` faz com que o `nmap` realize uma tentativa completa de conexão TCP, ou seja, concluindo o **3-Way Handshake**. Esse tipo de técnica **não** é furtiva, porém é útil em alguns cenários em que é necessário se passar por uma tentativa real de conexão.
#### Tipos de resposta
| Resposta                                           | Estado     |
| -------------------------------------------------- | ---------- |
| Resposta com pacote TCP SYN/ACK                    | `open`     |
| Resposta com pacote TCP RST                        | `closed`   |
| Nenhuma resposta (mesmo com retransmissão)         | `filtered` |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, 13) | `filtered` |

> [!redteam] TCP Scan + Proxy #redteam 
> Como um **TCP Scan** realiza o **3-way handshake** completo, utilizando chamadas do sistema como a `connect` no Linux, ele pode ser executado através de **proxies**. Isso permite realizar varreduras mantendo o anonimato do IP de origem e pode ajudar a evitar firewalls baseados em IP, já que o tráfego parecerá legítimo e virá do proxy.

> [!blueteam] Monitorando **TCP Scans** #blueteam 
> Por ser uma técnica de scan bem barulhenta, é fácil monitorar **TCP Scans**. Para isso, basta escrever uma regra no [[1. iptables]] que limite ou a quantidade de tentativas de conexões ou quantidade de conexões estabelecidas/parelelas.

### UDP Scan 
[source](https://nmap.org/book/scan-methods-udp-scan.html)

```shell
$ nmap -p [ports] -sU [host]
```

A opção `-sU` ativa o modo de `UDP Scan`. Para a maioria das portas, o `nmap` envia um pacote vazio, contudo para as portas mais conhecidas (53, 67 etc) um payload específico para o protocolo será enviado.

#### Tipos de resposta
| Resposta                                                      | Estado          |
| ------------------------------------------------------------- | --------------- |
| Qualquer resposta com pacote UDP (pouco comum)                | `open`          |
| Nenhuma resposta (mesmo após outras tentativas)               | `open/filtered` |
| ICMP unreachable (type 3, code 3)                             | `closed`        |
| Outro erro ICMP unreachable (type 3, code 1, 2, 9, 10, ou 13) | `filtered`      |
#### Ambiguidade do estado `open|filtered`

Essa técnica de scanning sofre de um problema significativo: serviços ativos numa porta **UDP** raramente respondem pacotes com payload vazio. Para contornar isso, `nmap` envia pacotes específicos para as portas mais conhecidas, como tentativa de obter alguma resposta. Por isso existe o estado `open|filtered`, pois o `nmap` é incapaz de determinar se a porta está aberta ou filtrada.

Uma tentativa de resolver essa ambiguidade é usar o submódulo de detecção de versões `-sV`. Basicamente o `nmap` envia **probes** personalizados para portas marcadas como `open|filtered` para provocar alguma resposta; isso é pouco **stealth**, pois gera bastante tráfego. Esse submódulo é bem complexo e vale a pena dar uma lida na [fonte](https://nmap.org/book/vscan.html).


> [!redteam] Cuidado com o `-sV` #redteam 
> Ativar o submódulo de detecção de versões para contornar a ambiguidade de portas `open|filtered` pode ser problemático devido ao "barulho" que ele gera na rede. O tráfego de pacotes pode aumentar bastante, devido à múltiplas tentativas e tamanho dos payloads personalizados enviados pelo `nmap`.

> [!blueteam] Configure sistemas de **IDS/IPS** #blueteam 
> Sistemas de detecção e prevenção de intrusão ([[5. IDS]]/[[5. IPS]]) são uma ótima maneira de detectar scannings, ainda mais os que são bastante barulhentos.

#### Lentidão no scanning UDP
 
A única forma de determinar se uma porta está fechada é caso o `nmap` receba um pacote ICMP do host alvo. Muitos sistemas possuem **rate limit**  para pacotes ICMP, limitando o número de respostas por segundo. Como o `nmap` necessita dessas respostas, o scan se torna muito lento devido à quantidade de tentativas feitas. Isso pode tentar ser contornado com as seguintes opções:
- `--top-ports` ou `-p` para limitar o número de portas scaneadas.
- `--scan-delay` para aumentar o delay entre cada teste, para evitar "triggar" o rate limit do servidor.
-  `--max-retries` ou `--host-timeout` para ajustar número de tentativas e timeout 


### FIN, NULL e Xmas Scan
[source](https://nmap.org/book/scan-methods-null-fin-xmas-scan.html)

Esses três tipos de scan exploram sistemas que estão em conformidade com a [RFC do protocolo TCP](https://www.rfc-editor.org/rfc/rfc793.txt). A exploração consiste no entendimento de dois requisitos importantes:
1. A RFC diz que se a porta do host estiver **fechada** e um pacote TCP enviado à ela não conter a flag `RST`, então o host deve responder com um `RST`. (*p 65, SEGMENT ARRIVES - If the state is CLOSED then...*)
2. A RFC diz que se a porta do host estiver **aberta** e um pacote TCP enviado à ela não conter a flag `SYN` ou `RST` ou `ACK`, então o host deve ignorar o pacote silenciosamente e não responder nada. (*p 66,  SEGMENT ARRIVES - If the state is LISTEN then... fourth other text or control*)

A partir deste dois requisitos conseguimos concluir que:
- Qualquer porta que esteja **fechada** e receber um pacote que **não** possua a flag `RST` responderá com um `RST`, justamente para indicar que a porta está fechada.
- Pacotes enviados sem a flag `SYN`, `RST` ou `ACK` para portas **abertas** não serão respondidos. Dessa forma, a porta está ou `open` ou `filtered`.

Há três jeitos de correspondermos aos requisitos estabelecidos pela RFC, resultando, portanto, em três tipos de scan:
1. `-sN`: **Null Scan**, consiste em mandar o cabeçalho `flags` zerado.
2. `-sF`: **FIN Scan**, consiste em mandar apenas a flag `FIN`.
3. `-sX`: **Xmas Scan**, consistem em mandar as flags `FIN`, `PSH` e `URG`.

Este tipo de scanning obviamente não funciona com portas **UDP**.
#### Tipos de resposta
| Resposta                                              | Estado          |
| ----------------------------------------------------- | --------------- |
| Nenhuma resposta (mesmo após outras tentativas)       | `open/filtered` |
| Resposta com TCP RST                                  | `closed`        |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, or 13) | `filtered`      |

> [!redteam] Conformidade com RFC #redteam 
> A maioria de hosts UNIX-like estão em conformidade com a RFC, dessa forma, essas técnicas de scan podem ser bem aproveitadas contra esse tipo de sistema. O comportamento pode ser testado, inclusive, com o [[1. hping3]] + servidor apache:
> ```shell
> $ hping3 -n 1 -p 80 -F [host]
> ```
> Se a porta estiver `closed`, como não estamos enviando a flag `RST`, então o host provavelmente vai nos retornar um `RST`. Se a porta estiver `open`, como não estamos enviando a flag `SYN` para iniciar uma conexão, então o host irá ignorar o pacote silenciosamente. O mesmo comportamento ocorre enviando nenhuma flag ou enviando as flags `FIN`, `PSH` e `URG` simultaneamente.

> [!redteam] Como lidar com `open|filtered` #redteam 
> Caso o host possua uma regra de [[5. Firewall]] para dropar pacotes na porta de destino, um **FIN/NULL/Xmas** scan identificará que a porta está `open|filtered`. Isso pode ser testado ao criar a seguinte regra no [[1. iptables]] e depois rodar o `nmap`:
> ```shell
> $ iptables -A INPUT -p tcp --dport 80 -j DROP
> ```
> Por este motivo é importante combinar diferentes tipos de scanning. Neste caso, [[#ACK Scan]] pode ser útil se executado junto.

### ACK Scan
[source](https://nmap.org/book/scan-methods-ack-scan.html)

Tipo de scan focado em detectar regras de Firewall, não para descobrir portas abertas. Consiste em enviar um raw packet TCP apenas com a flag `ACK`. Portas que estiverem abertas ou fechadas responderão com `RST` a não ser que estejam sendo filtradas por um Firewall. Este tipo de filtragem obviamente não funciona com portas **UDP**. 
#### Tipos de resposta
| Resposta                                              | Estado       |
| ----------------------------------------------------- | ------------ |
| Resposta com TCP RST                                  | `unfiltered` |
| Nenhuma resposta (mesmo após outras tentativas)       | `filtered`   |
| ICMP unreachable (type 3, code 1, 2, 3, 9, 10, or 13) | `filtered`   |

> [!info] Desambiguar `open|filtered` com **ACK Scan**
> Esse tipo de scan é útil para tentar desambiguar portas que foram identificadas como `open|filtered` por outras técnicas de scanning. Por exemplo, se uma porta scaneada com [[#FIN, NULL e Xmas Scan|FIN Scan]] retornar `open|filtered`, mas retornar como `unfiltered` (que significa `open` ou `closed`) num **ACK Scan**, então logicamente essa porta só pode estar `open`.
> 

> [!redteam] Trabalhoso para ser filtrado #redteam 
> Raw packets contendo apenas a flag `ACK` são comuns em conexões TCP legítimas, pois são usados para confirmar recebimento de dados. Contudo, esse tipo de pacote não indica qual [[5. Host]] iniciou a conexão, dessa forma, é difícil para [[5. Firewall#Stateless Firewall|Firewalls Stateless]] identificarem se é um pacote legítimo ou não.

> [!blueteam] Stateful Firewalls #blueteam 
> [[5. Firewall#Stateful Firewall|Stateful Firewalls]], por manterem uma tabela de conexões  abertas, conseguem identificar raw packets `ACK` ilegítimos. A desvantagem é que esse tipo de firewall consome muitos recursos da máquina e podem sofrer ataques [[7. Denial of Service|DoS]] por table exhaustion. Além disso podem impactar a velocidade do tráfego de pacotes devido ao overhead para verificar se a conexão existe.
