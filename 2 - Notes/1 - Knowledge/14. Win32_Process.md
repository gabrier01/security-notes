O **WMI (Windows Management Instrumentation)** é a infraestrutura de gerenciamento do Windows. Permite consultar e manipular praticamente qualquer componente do sistema (hardware, SO, processos, serviços, logs) de forma programática. Tudo é modelado como **classes**, organizadas em **namespaces** (o padrão é `root\cimv2`), e consultado com **WQL**, uma linguagem parecida com SQL.

`Win32_Process` é a **classe WMI que representa um processo** em execução. Cada instância é um processo, com propriedades (`ProcessId`, `Name`, `CommandLine`...) e alguns **métodos**.

# Win32_Process.Create

O método `Create` da classe **cria um novo processo**. É essa a primitiva de execução: chamá-lo num host remoto significa executar código naquele host.

```powershell
Invoke-CimMethod -ClassName Win32_Process -MethodName Create `
  -Arguments @{ CommandLine = "cmd.exe /c whoami > C:\out.txt" } `
  -ComputerName [alvo]
```

Localmente também é possível via `Get-CimInstance`/`Get-WmiObject` ou o antigo `wmic.exe`. Remotamente, o WMI trafega sobre **DCOM** (RPC na porta `tcp/135` + portas altas dinâmicas) ou **WinRM** (`tcp/5985`/`5986`).

# Relevância no pentest

É o motor de execução por trás do `wmiexec` (Impacket). Comparado ao [[14. Service Control Manager|SCM]] (usado pelo PsExec), o WMI é mais furtivo:

- **Não solta binário em disco** nem cria serviço, portanto não gera o evento `7045`.
- Roda como o **usuário administrador conectado** (via `WmiPrvSE.exe`), e não como SYSTEM.
- Ainda exige **credenciais de administrador local** no alvo.

> [!redteam] WMI não retorna a saída
> `Win32_Process.Create` só devolve um PID, não o stdout do comando. Por isso o `wmiexec` redireciona a saída para um arquivo e depois o lê via SMB ([[14. Compartilhamento Administrativo|ADMIN$]]). Ou seja: WMI para executar, SMB para ler o resultado.

Além de execução, o WMI é muito usado para enumeração (software, patches, antivírus) e para **persistência** (via WMI Event Subscriptions).
