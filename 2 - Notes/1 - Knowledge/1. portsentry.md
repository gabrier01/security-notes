Ferramenta de segurança para detectar varreduras de portas. É capaz de fazer log de tentativas de reconhecimento, adicionar o IP do atacante numa lista de bloqueio (`hosts.deny`, [[1. iptables]] etc) e executar comandos personalizados para responder à ameaças.

```shell
# iniciar daemon
$ service portsentry start

# iniciar executando o binário
$ portsentry -tcp
```


> [!blueteam] Monitorar diferentes tipos de bloqueios
> Executar o binário diretamente permite monitorar tipos diferentes de scanning de portas. Por exemplo `SYN Scans`(`-stcp`), `TCP Connect Scans`(`-tcp`), `UDP Scans`(`-udp`) etc.
> 
> Mais informações sobre os tipos de scanning podem ser encontradas em [[9. nmap#Técnicas de Port Scanning|nmap - Técnicas de Port Scanning]].

# Funcionamento

O `portsentry` funciona basicamente como um [[7. Honeypot]]. Para que sua detecção funcione ele precisa "bindar" a porta e escutar por pacotes. Portanto, ele só é capaz de monitorar portas que **não** estão sendo utilizadas.

Assim que iniciado, mesmo através do binário, a aplicação irá executar um subprocesso em background escutando as portas especificadas no arquivo de configuração. Múltiplas execuções de `portsentry` podem ser feitas, cada uma para um tipo diferente de monitoramento.

# Configuração

Por padrão, o `portsentry` não toma nenhuma ação contra possíveis atacantes, apenas faz logs em `var/log/syslog`. Contudo, este comportamento pode ser alterado pelo arquivo  `portsentry.conf`, encontrado em `/etc/portsentry`.

> [!tip] Ler o arquivo
> O arquivo de configuração do `portsentry` é bem descritivo, com muitos comentários, recomendo a leitura para entendimento melhor de todas as configurações que podem ser feitas

## Portas monitoradas

No arquivo de configuração, é possível encontrar as variáveis `TCP` e `UDP`. Elas controlam a lista de portas que a ferramenta tentará abrir para monitorar pacotes suspeitos.

## Controle de ação

As variáveis `BLOCK_UDP` e `BLOCK_TCP` controlam a ação que o `portsentry` tomará caso detecte comportamento suspeito. Cada valor abaixo corresponde à um modo de ação:
- `"0"`: não faz nada, apenas log
- `"1"`: bloqueia o pacote seguindo a ação definida pela variável `KILL_ROUTE` (pode bloquear via [[1. route]] ou [[1. iptables]])
- `"2"`: executa um comando personalizado especificado em `KILL_RUN_CMD`.

## Controle do tipo de bloqueio

Se as variáveis `BLOCK_UDP` ou `BLOCK_TCP` estiverem com o valor `"1"`, então o `portsentry` irá executar o comando especificado em `KILL_ROUTE`. O arquivo de configuração possui uma série de exemplos de `KILL_ROUTE` comentados. O próprio desenvolvedor recomenda executar uma ação com um packet filter, como o [[1. iptables]]. Por exemplo, a linha abaixo:

```
# iptables support for Linux
KILL_ROUTE="/sbin/iptables -I INPUT -s $TARGET$ -j DROP"
```

O `KILL_ROUTE` acima cria uma regra na chain `INPUT` para rejeitar silenciosamente qualquer pacote recebido por `$TARGET$`.

> [!warning] Apenas um por vez
> Apenas uma linha de `KILL_ROUTE` deve estar sem comentário por vez. 

## Arquivo hosts.deny

A variável `KILL_HOSTS_DENY` indica o formato da linha que será adicionado no arquivo [[2. _etc_hosts.deny|/etc/hosts.deny]].

Note que, mesmo que o host seja adiciona ao `hosts.deny`, port scannings ainda são possíveis se nenhum outro tipo de bloqueio (como bloqueios de rota ou uso de packet filters) for feito.

## Controle de tempo de reação

A variável `SCAN_TRIGGER` controla o "tempo" de reação perante um port scanning. O valor `0`, definido por padrão, indica que o `portsentry` irá reagir **imediatamente**, executando a ação especificada em `BLOCK_UDP`/`BLOCK_TCP`.

Valores maiores do que zero indicam que a ferramenta irá esperar `x` conexões antes de realizar a ação.
