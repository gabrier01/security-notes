**Simple Network Management Protocol** (SNMP) é um protocolo da camada de aplicação para gerenciamento de dispositivos de rede. Através de serviços que implementam este protocolo é possível consultar e modificar informações sobre um dispositivo conectado na rede, seja ele um computador, roteador, switch, impressoras, versões de softwares etc. Além disso, serviços SNMP podem ser configurados para proativamente enviarem **traps** (ou alertas) caso o dispositivo atenda determinada condição.

Interações do protocolo SNMP são realizadas entre **Manager** e **Agent**, sendo o primeiro quem envia consultas e recebe traps e o segundo quem recebe as consultas e envia as traps.  

Por padrão, **agents** SNMP escutam na porta `udp/161` para recebimento de consultas enquanto managers **escutam** na porta `udp/162` para recebimento de traps.

# Informações dos dispositivos e OID

Entre as informações que podem ser consultadas e/ou modificados se encontram: 
- uso de CPU e memória;
- tabela ARP;
- diversos contadores (por exemplo quantidade de pacotes icmp recebidos);
- informações do dispositivo como uptime, nome etc;
- interfaces de rede;
- processos em execução;
- portas ativas;
- etc.

Cada item possui um **OID (Object Identifier)** que é um código de identificação. Um OID é estruturado num formato de árvore hierárquica composta por números separados por pontos, como por exemplo `1.3.6.1.2.1.1.3.0` que representa o OID da instância do objeto que armazena o up-time da máquina. A árvore hierárquica deste OID pode ser representada da seguinte forma:

```shell
1 (iso) # raiz da árvore de OIDs
 └─ 3 (org) # Organizações
      └─ 6 (dod) # Departamento de Defesa dos EUA (onde ARPANET se originou)
           └─ 1 (internet) # Estrutura SNMP/Internet
                └─ 2 (mgmt) # Objetos gerenciados por orgs de padronização
                     └─ 1 (mib-2) # MIB-II (RFC 1213), base do SNMPv1/v2.
                          └─ 1 (system) # informações sobre sistema
                               └─ 3 (sysUpTime) # objeto uptime
                                    └─ 0 (instance) # índice em que o valor está contido (para tabelas, pode conter números sequenciais, como exemplo uma lista de interfaces de rede)
```
> A hierarquia completa de OIDs pode ser encontrada em [Global OID reference database](https://oidref.com/1).*

Além de um código numérico, um OID também possui uma versão simbólica legível. O exemplo acima seria o símbolo `sysUpTime.0` ou `sysUpTimeInstance`. Contudo, para trabalhar com os símbolos OID, é necessário a instalação dos arquivos **MIB**.

# Management Information Base (MIB)

Uma MIB é um arquivo de texto contendo detalhes sobre OIDs. Os detalhes incluem descrição, tipo dos valores da instância, caminho da hierarquia, se é readonly ou não etc.

Os arquivos MIB podem ser adquiridos ao instalar o pacote correto para o sistema operacional em questão. Em sistemas Debian, isso pode ser feito ao instalar `snmp-mibs-downloader`:

```shell
$ apt install snmp-mibs-downloader
```

Em algumas ocasiões é necessário verificar se o arquivo `/etc/snmp/snmpd.conf` bloqueia o carregamento das MIBs. Neste caso, é necessário ou comentar a linha `mibs :` ou adicionar a linha `mibs +ALL`.


> [!tip] Visualizar hierarquia completa
> Para visualizar toda a árvore de hierarquia OID, basta usar o comando `snmptranslate -Tp | less`. É também possível especificar uma parte da hierarquia para exibir só o que estiver abaixo dela: `snmptranslate -Tp 1.3.6.1.2.1.1 | less`

## Tradução de OIDs

Após a instalação das MIBs podemos traduzir tanto um OID numérico para sua representação simbólica, quanto sua representação simbólica para seu OID numérico. Isto é feito com o comando [[1. snmptranslate]]:

```shell
$ snmptranslate [oid_numeric]
# $ snmptranslate 1.3.6.1.2.1.1.3  
# SNMPv2-MIB::sysUpTime

$ snmptranslate -On [oid_symbol]
# -On: faz com que o output saia em formato numérico
# snmptranslate -On SNMPv2-MIB::sysUpTime
# .1.3.6.1.2.1.1.3
```

## Detalhes de um OID

Com o mesmo comando `snmptranslate` podemos acessar a entrada de um OID em um arquivo MIB e obter seus detalhes.

```shell
$ snmptranslate -Td [oid_numeric|oid_symbol]
# $ snmptranslate -Td 1.3.6.1.2.1.1.3
# ou
# $ snmptranslate -Td SNMPv2-MIB::sysUpTime

# SNMPv2-MIB::sysUpTime
# sysUpTime OBJECT-TYPE
#  -- FROM       SNMPv2-MIB
#  SYNTAX        TimeTicks
#  MAX-ACCESS    read-only
#  STATUS        current
#  DESCRIPTION   "The time (in hundredths of a second) since the
#            network management portion of the system was last
#            re-initialized."
# ::= { iso(1) org(3) dod(6) internet(1) mgmt(2) mib-2(1) system(1) 3 }
```

Note que em alguns casos talvez seja necessário especificar o nome do arquivo MIB em que a entrada para o OID se encontra, como no caso do `SNMPv2-MIB::sysUpTime`, em que o valor antes dos `::` é o nome do arquivo (módulo MIB). 

Com as MIBs devidamente instaladas, demais comandos apresentados nas próximas seções funcionarão tanto para os OIDs numéricos quanto para suas representações simbólicas.


# Community Strings

Nas versões v1 e v2c do SNMP, **community strings** são texto puro utilizado para autenticação simples e controle de autorização entre manager e agent. Elas determinam se o agent reconhece o manager e se este tem permissão apenas para leitura (`ro`) ou leitura/escrita (`rw`) sobre os OIDs expostos.

As community strings podem ter configuração granular, ou seja, serem disponibilizadas para um IP (ou range de IP) específico e/ou poderem acessar OIDs específicos. 

Exemplos de community strings são: `public`, `private`, `manager`, `secret`, `cisco`, `access`, `juniper` etc.

As configurações de community strings e demais outras configurações do serviço podem ser encontradas no arquivo `/etc/snmp/snmpd.conf`.

> [!redteam] Community strings padrão
> As community strings variam conforme fabricante de um dispositivo, desta forma é sempre uma boa prática verificar o manual do fabricante para identificar qual community padrão é utilizada. Muitas vezes o sysadmin apenas copia e cola a padrão ao invés de criar uma personalizada.

> [!blueteam] Utilizar versão 3 do SNMP
> Versões mais recentes do SNMP, como a v3, depreciaram o uso de community strings para um formato mais robusto de autenticação utilizando par usuário/senha e criptografia. Caso não seja possível a atualização para versões mais recentes, procure restringir quais IPs uma community está disponível e que tipos de OIDs podem ser acessados por ela.

## Enumeração de community strings

É possível enumerar community strings de um host utilizando a ferramenta [[1. onesixtyone]]. Ela recebe uma lista de communities para serem testadas e um IP ou netmask:

```shell
$ onesixtyone -c [file] [ip|netmask]
# $ onesixtyone -c communities.txt 192.168.0.0/24
```

> [!note] Community strings são case-sensitive
> Note que serviços SNMP interpretam o texto de uma community string como case-sensitive, dessa forma, `public` e `Public` são diferentes.

# Varredura de informações

Com uma community string válida em mãos, é possível fazer uma varredura da hierarquia de OIDs de um determinado host e obter todas as informações possíveis que a community string utilizada consegue acessar.

## `snmpwalk`

 Uma das ferramentas aptas para varrer hierarquias é a [[1. snmpwalk]]:

```shell
$ snmpwalk -v[version] -c [community] [host] [oid_root]
# $ snmpwalk -v2c -c public 192.168.1.10 1.3.6.1
# > Varre tudo dentro da hierarquia 1.3.6.1
```

- `-v[version]`: versão do SNMP; `-v1`, `-v2c`, `-v3`
- `-c [community]`: nome da community string; `-c public`
- `[host]`: IP ou domínio
- `[oid_root]`: parte de uma hierarquia para fazer a varredura ou OID completo; se nenhum valor for informado, o padrão é o início da hierarquia `mib-2`, ou seja, `1.3.6.1.2.1`.

## `snmp-check`

A ferramenta [[1. snmp-check]] também pode ser utilizado para fazer varreduras em hierarquias OID de um host. A vantagem dessa ferramenta é o formato organizado em que as informações são retornadas.

```shell
$ snmp-check [host] -c [community]
```


# Tipos de OID

O "leaf-node" de uma hierarquia OID, isto é, o OID que de fato contém algum dado, pode ser um objeto escalar (scalar) ou tabela (table). 

### Objeto escalar

Um objeto escalar contém apenas uma **instância**, representada pelo índice `0`. É esta instância que contém o valor do objeto representado pelo OID. É o caso do `sysUpTime.0`:

```shell
$ snmpwalk -v[version] -c [community] [host] sysUpTime.0
# sysUpTimeInstance = Timeticks: (116748) 0:19:27.48
```

Note que tentar executar o comando acima para `sysUpTime.1` retornará nada.

> [!tip] Omitir o índice da instância com `snmpwalk`
> O comando `snmpwalk`, por ser um "varredor" de hierarquia, não necessita receber o índice da instância. É possível especificar apenas parte da hierarquia OID (tanto símbolo quanto numérico) para que ele percorra ela inteiramente. Neste caso, `snmpwalk -v1 -c public [host] sysUpTime` retornaria normalmente o valor contido na instância `0`. 

### Objeto tabela

Um objeto tabela, em contrapartida ao escalar, possui mais de uma instância, simulando uma espécie de lista. Isto ocorre, por exemplo, com o símbolo `ifDescr`, que representa uma tabela contendo as descrições de interfaces de rede.

```shell
$ snmpwalk -v[version] -c [community] [host] ifDescr
# ifDescr.1 = STRING: lo
# ifDescr.2 = STRING: eth0
# ifDescr.3 = STRING: eth1
```

Note que este objeto escalar retornou três entradas com índices entre `1` e `3`. Os índices da tabela utilizada neste exemplo podem ser encontrados no símbolo `ifIndex`.  Para acessar uma interface específica, basta especificar seu índice, como `ifDescr.1`.

## Tipos de valores de instâncias

Sendo um objeto escalar ou tabela, os valores de suas instâncias possuem tipos bem definidos. Saber esses tipos será útil para manipular os valores com [[1. snmpset]], que será visto na seção [[#Alterar o valor de um OID]].

Os tipos possíveis são:

| Tipo SNMP        | Código `snmpset` | Descrição                                                                | Exemplos de OIDs                |
| ---------------- | ---------------- | ------------------------------------------------------------------------ | ------------------------------- |
| **INTEGER**      | `i`              | Número inteiro, pode ter valores limitados por enumeração                | `ifType`, `sysServices`         |
| **OCTET STRING** | `s`              | Textos, endereços MAC, números codificados                               | `sysName`, `sysLocation`        |
| **Unsigned32**   | `u`              | Inteiro não-negativo, usado para contadores que podem diminuir           | `ifSpeed`                       |
| **Counter32**    | -                | Contador crescente, reinicia ao atingir limite (32 bits)                 | `ifInOctets`, `ifOutErrors`     |
| **Counter64**    | -                | Contador crescente 64 bits (SNMPv2)                                      | `ifHCInOctets`, `ifHCOutOctets` |
| **TimeTicks**    | `t`              | Inteiro representando tempo em centésimos de segundo desde inicialização | `sysUpTime`                     |
| **OID**          | `o`              | Referência a outro OID                                                   | Tabelas hierárquicas, índices   |
| **IpAddress**    | `a`              | IPv4 (4 bytes)                                                           | `ipAdEntAddr`                   |
| **Bits**         | `b`              | Conjunto de flags binárias                                               | `ifAdminStatus`, `ifOperStatus` |

# Alterar o valor de um OID

Tendo listado todos os OIDs possíveis no processo de varredura, agora é possível tentar alterar o valor contido neles. Alguns OIDs são readonly por padrão, mesmo que a community string permita escrita; isso pode ser identificado ao detalhar o objeto com `snmptranslate -Td [oid]`. Já outros permitem a edição com o utilitário [[1. snmpset]]:

```shell
$ snmpset -v[version] -c [community] [host] [oid] [type] [value]
# $ snmpset -v2c -c public 192.168.0.10 sysContact.0 s "New Sys Contact Name"
```

- `[type]`: tipo SNMP do valor do objeto; ver [[#Tipos de valores de instâncias]]
- `[value]`: valor a ser atribuído ao objeto; depende de `[type]`.

Note que alguns tipos não podem ser modificados por se tratarem de informações **readonly**, como é o caso dos contadores.
