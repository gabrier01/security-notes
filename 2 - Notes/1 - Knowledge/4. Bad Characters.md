**Bad characters** (bad chars) são bytes que não podem aparecer no [[7. Payload|payload]] de um exploit porque o programa alvo os trata de forma especial e acaba cortando, alterando ou parando de ler a entrada ali. Se um bad char cair no meio do shellcode ou no endereço de retorno de um [[4. Buffer Overflow]], a exploração quebra.

O clássico é o **null byte** `\x00`, que em C termina uma string, mas dependendo de como a entrada é processada outros também atrapalham: `\x0a` (`\n`, newline), `\x0d` (`\r`, carriage return) e `\xff` são suspeitos frequentes.

# Como identificar

A ideia é mandar todos os 256 bytes possíveis (de `\x00` a `\xff`) logo depois do offset e, com o debugger, comparar o que realmente chegou na memória com o que foi enviado. Onde a sequência for interrompida ou um byte estiver trocado, aquele byte é um bad char. Remova, reenvie e repita até a lista completa passar intacta.

O `\x00` já pode ser deixado de fora desde o começo, porque quase sempre é bad char.

> [!tip] Lista base para colar no exploit
> Uma lista com todos os bytes menos o `\x00` está em [[badchars]], pronta pra usar no teste. Vá removendo os que forem corrompendo a entrada.

# Uso no exploit

Depois de saber os bad chars, dois pontos usam essa informação:

- **Endereço de retorno**: escolha um `jmp esp` cujo endereço não contenha nenhum bad char.
- **Shellcode**: gere o payload com [[1. msfvenom]] excluindo os bad chars com `-b`. O `msfvenom` usa um encoder pra reescrever o shellcode sem esses bytes.

```shell
$ msfvenom -p [payload] LHOST=[lhost] LPORT=[lport] -b '\x00\x0a\x0d' -f c
```

- `-b`: lista de bad chars a evitar
- `-f c`: formato de saída (array em C, fácil de colar no exploit)
